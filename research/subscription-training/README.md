# 有限 L2 订阅下的机器学习训练与实盘对齐

## 目标与背景

研究始于2026-09-19：在有限实时 L2 订阅下，检验昨日信息能否改善盘前选池，并为后续
“分配—观察—决策—执行”验证建立信息边界。本卷宗保存候选及结论，研究治理见
[research_workflow](../../docs/engineering/research_workflow.md)；正式语义仍由 `docs/` owner 拥有。
背景见[标签讨论](../label-design/README.md#24-盘后全市场数据与实时订阅约束)、
[假设设计](../hypothesis-design/README.md)及[14:30 卷宗](../stock-1430/README.md)。

已确认：P 为 T 的前一正式交易日，P 21:00 获取全市场历史 L2 与日频数据；实时订阅按
`(symbol, topic)` 收费/限额，切换不补历史。交易目标、决策/持有期、资金与风险、套餐及
topic 组合仍待定。信息正确、预测改善、可实现净收益和运行可用性须分别验证。

先通过下列索引定位假设，再按 Evidence 读取对应 Notebook 的说明单元。需要复现时使用
说明中绑定的冻结版本；当前文件与历史归档的代码、输入不能互相替代。读取方式见
[研究工作流](../../docs/engineering/research_workflow.md#写入与按需读取)。

## 共同研究边界

预测改善、实际接收一致性、观察价值与可实现净收益分别验证；价格或排名代理不证明成交。
选池只用决策时可见的信息，未来标签缺失不改变推理候选；预处理、拟合与模型就绪遵守当时
的时间边界。历史修订数据与假设接收时间不能冒充当时实际可得的版本。
按完整日期区分开发与最终验证；已查看区间的复跑、修复和补录不增加独立确认次数。
共同方案、时钟约束、样本定义及早期接口核对见
[原研究边界](validation.ipynb#research-boundaries)，L2 覆盖见 [H06 核对](next_day_high.ipynb#h06-l2-coverage)。
正式编排仍以 [offline_workflow_contract](../../docs/offline_workflow_contract.md) 为准。
Notebook 中当时“保持 open”等表述属于历史说明，当前采用候选状态只由本卷宗对应段落
维护；本次整理不回写冻结证据，也不产生新的实验或采用决定。

## H01 信息边界的可执行验证

- Hypothesis: 完整 key、可用时间及生效订阅裁剪可拒绝不可见信息，并保持合法事件前缀
  不受未来数据改变；现有日期/全市场分钟视图不足以证明这一点。
- Scope: 自包含反例、现有公开 API 复现与候选断言；不含 MQTT、生产修复、真实 SLA 或交易。
- Acceptance（运行前固定）: 展示日频两 key 接口不验证 decision timestamp；候选三 key
  拒绝错位；拒绝晚标签/晚模型及未订阅/确认前/晚到消息；同股三 topic 占三份额度；
  状态未建立不能冒充完整观察；未来 label 缺失不改变选池；训练/推理复用预处理状态。
- Evidence（2026-09-19，本地 draft）: [`validation.ipynb`](validation.ipynb) 的8组断言全部
  通过，覆盖冷启动、窗口中断和未来污染。两 key 行为符合现有日频职责，不构成其缺陷。
  观察窗口/订单簿只验证可用性谓词；源码及恢复基线见 H02 归档。
- Conclusion: 本轮自包含边界验证已完成，反例通过；生产链路、订单簿重建与真实历史
  接收一致性未验证。
- Next: 后续研究：获得实际接收、订阅、处理及模型就绪日志和确定的盘中策略后，验证
  同事件前缀的 batch/stream 输出及故障复演；假设到达时间不能升级为观测事实。

## H02 昨日信息能否改善初筛

- Hypothesis: 仅用 P 的日频及历史 L2，预注册学习器能相对简单规则改善次日池的未来排名。
- Depends on: 日频输入及 [stock-1430 H03 特征/标签](../stock-1430/README.md#h03)；
  实际输入、版本及历史适用边界以冻结证据为准。
- Scope: 固定机会代理和50个 trans topic 的预测/名单诊断；不含真实成交、净收益、观察
  价值、套餐采用、全日 L2 或长期稳定性。
- Acceptance: 至少50个最终日、两方 pooled 标签覆盖各≥98%、保守均值差≥0.02，且
  5-session circular block bootstrap 单侧95%下界>0；完整参数与停止条件见冻结方案。
- Evidence: [冻结方案与停止条件](validation.ipynb#h02-protocol)、
  [79日失败结果及冻结归档](validation.ipynb#h02-evidence)、[精确复跑](validation.ipynb#h02-reproduce)。
- Conclusion: 本轮固定初筛实验已完成且可恢复，冻结候选未通过样本外初筛门槛；这不构成
  所有 L2 无效或正式 rejection。实际接收、观察价值及净 alpha 未验证。
- Next: 后续研究：历史扩展、命中诊断和目标变更分别见 H04–H06；已消费79日只可用于开发，
  新的确认性主张须预注册并使用未消费信息。

## H03 已收逐笔的分批与离线特征一致性

- Depends on: H01 信息边界，不依赖 H02 预测有效。
- Hypothesis: 按订阅/接收截止裁剪，在连续接收段内重建 tick-rule，可使分批输入与离线
  重放的分钟事实相同，且后续消息不改变过去快照；不能继承全日方向或按到达顺序定方向。
- Scope: 复用 `Access.trades` 和分钟 builder，隔离检查 `2026-08-25` 的600000/000001
  正成交及 `14:00..14:30`；价格/量真实，接收/订阅为人工情景。不含供应商实时解析、
  真实延迟、order/market、订单簿、预测价值或部署。
- Acceptance: 固定情景的分批/离线事实一致、守恒及污染反例通过；批次、容差和
  截止点按[原验收条件](reception_validation.ipynb#h03-scenarios)，不改变既定精度。
- Stop: 技术失败保留并同验收重跑，不改变 H02 的预测或 alpha 门槛。
- Evidence: [人工接收情景](reception_validation.ipynb#h03-scenarios)、
  [90次对照、反例及归档恢复](reception_validation.ipynb#h03-evidence)。
- Conclusion: 本轮固定接收情景验证已完成，同前缀一致性成立；裁剪、重置与事件排序须在
  聚合前完成。
  研究实现缓存前缀并重算，未验证生产吞吐/内存/恢复、真实接收或经济价值，其输出不能
  冒充正式全日分钟对象。
- Next: 后续研究：取得实际日志并固定字段、乱序/丢包/重复/恢复规则后复演；交易目标及
  新验证数据就绪后再接入完整训练—分配—决策实验。

## H05 固定名单的机会命中诊断

- Depends on: H04 冻结面板、预测、名单和选择。
- Hypothesis: 平均排名接近0.5仍可能富集前部机会；固定名单的 Precision@K/Lift 可直接
  检验，Recall/F1 补充覆盖。用户于2026-09-22同意按机会命中评价。
- Scope: 原102日开发段与17日后续段只读补算，不重训或改名单/策略；结果后的质量补查
  另读六个正式对象并隔离复制。不含分类训练、原始/净收益标签、观察价值、真实接收及成交。
- Acceptance: 名单、计数、缺失边界及执行检查按[冻结方案](opportunity_metrics.ipynb#h05-protocol)；
  主差均值>0且5日区块单侧95%下界>0，至多称探索性支持；两段已查看且未校正多重比较。
- Stop: 固定范围补算一次；技术错误同口径修复，不随结果调整 K、阈值或候选。
- Evidence: [指标及验收](opportunity_metrics.ipynb#h05-protocol)、
  [原结果、质量补查与归档](opportunity_metrics.ipynb#h05-evidence)；修复后重验见 H04。
- Conclusion: 本轮固定名单诊断已完成。命中指标提供了平均排名之外的重要信息：
  H04 原主候选未能富集前10%收益机会，当前八候选在开发段也未显示该目标的机会密度优势。
  训练时优化排名回归与评价时
  捕获尾部事件是不同目标；这解释了为何需要另提事件概率候选，但不是已经验证的失败机制。
  用户同意执行指标研究，不表示已采用机会标签、K、模型、交易策略或套餐。
  H04 的冻结选择与失败记录保留，经济解释受新增质量发现限制；
  净 alpha 和观察价值未验证。
- Next: 后续独立问题：旧重复文件的生成或转存环节仍待追溯。事件概率有限对照已形成
  H07，泛化仍须新验证信息；交易机会和观察价值须先明确执行、成本、风险及有/无L2策略。

没有盘口价差、完整深度、委托及撤补特征；覆盖核对见
[H06 说明](next_day_high.ipynb#h06-l2-coverage)。`Level2Market` 值得作为独立信息增量方向，
`Index` 适合市场背景、交互及基准评价。H07/H08 对现有成交特征的结果不能推广为这两类
数据无效，也不能从字段丰富推导出它们能提升机会命中率、泛化或净收益。

使用边界：

- 盘前选池只用此前已可得的 P 及更早数据，不能加入 T 日盘口或指数结果。盘中候选须按
  生效订阅、实际接收和处理截止裁剪；历史全市场文件不能补看切换订阅前的数据，
  `LocalTimeStamp` 不能替代策略接收日志。`Index/Level2Market` 的时间及可用性映射尚未正式定义。
- 证券出现于文件不等于当时可交易；股票资格沿用 H08 的时间边界。非股票、盘前零价格、
  空盘口和同时间多帧需按相应来源语义处理，不能直接混入股票特征或按时间戳自动去重。
  截至决策时的累计量不能跨快照求和，未来全天高低点只能用于标签或事后评价。
- 委托、成交、撤单、盘口快照是互补观察，不是可直接互换的事实。恢复订单身份、撤单方向、
  事件顺序和初始状态前，不将挂单变化解释为逐单撤补、真实资金流或可成交队列。

后续若启动增量研究，先固定目标、模型、候选特征及开发/未消费验证日期，在相同观察窗口与
成交基线上分别加入盘口组、指数组；扩大到完整昨日另做比较，避免把时段覆盖与信息类型混为
同一增量。订单/撤单先验证恢复边界；当日 L2 的行动价值还需要固定执行策略、普通行情对照及
订阅预算，并按完整交易效用评价。上述方向尚未启动，未新增训练、回放或正式入口。

#### 深圳撤单的利用边界与后续建议

2026-10-03 补充。现有成交链路排除撤单符合
[正成交契约及其原因说明](../../docs/data/level2_normalization.md#trade-cancel-filter)。
当前缺少的是撤单事件的独立消费和特征；可从原始 `SZ_Trade` 另行提取，不应通过放宽
成交过滤来实现。以下是未来研究建议，未形成可执行实验或采用决定，不新增 H、正式
dataset、parser 或训练入口。

基础撤单统计不要求先完整处理 `SZ_Order`；需要哪些数据取决于要回答的问题：

| 候选信息 | 是否需要关联 `SZ_Order` | 使用前提 |
|---|---|---|
| 窗口内撤单记录数 | 不必 | 核对撤单编码、事件时间、覆盖及重复情况；记录数不等于独立订单数 |
| 撤单数量及其相对成交数量 | 不必 | 确认撤单行数量的含义、单位和有效性，比较同一股票、同一窗口 |
| 买方与卖方撤单数量、不平衡 | 未必 | 验证 `BuyNo/SellNo` 哪侧有效能否可靠表示撤单方向；当前 processed 深圳 `side` 为空 |
| 某批委托的撤单比例、订单存续时间、撤补行为 | 需要 | 验证订单关联键、编号命名空间、事件顺序及完整性，并定义统计窗口或订单范围 |
| 逐单剩余量、队列和完整订单簿 | 需要委托与成交、撤单等完整事件 | 除可靠关联外，还须验证初始状态、通道及事件覆盖；文件和编号存在不等于可以完整恢复 |

解释与实现边界：

- 撤单数量除以成交数量表示撤单相对成交的活跃程度，不表示多少比例的委托被撤销。
  后者需要委托作为分母；撤单价格乘数量也不能称为成交额或资金净流出。
- 独立撤单解析不能直接沿用成交的 `price > 0` 筛选。先核查撤单数量与时间，使用价格的
  指标另行确认价格含义及有效性；未知价格可能仍伴随有效撤单数量，尚未定义正式处理规则。
- 订单关联沿用[归一化 owner 的限制](../../docs/data/level2_normalization.md)：
  `order_id=SubSeq` 不是订单身份或 join key，`MainSeq/SubSeq` 不提供已验证的全局唯一性，
  不能据此自动去重或宣称订单链恢复成功。
- 撤单可用于研究未成交意愿的变化，但买方撤单不直接证明看空或资金流出，卖方撤单也不
  直接证明看多；重新报价等行为需要结合后续委托研究，且不能把决策后的事件用于当时特征。

建议顺序：

1. 保留当前 32 列成交 L2 作为基线，不改变其定义或成交标签口径。
2. 完成源数据核查后，先在隔离研究中计算不依赖订单关联的撤单记录数、数量及相对成交
   活跃程度；沿用截至 P 日 14:30 的 5/15/30/60 分钟窗口，方向确认后再考虑买卖撤单不平衡。
3. 将撤单组与 `Level2Market` 盘口组分别加入相同成交基线，区分各自的信息增量。快照适合
   价差、深度和盘口不平衡；[已核查的 2026-09-22 文件](../../docs/data/source_contract.md#level2-delivery-contents)
   六个 `Withdraw*` 字段全空，不能替代逐笔撤单统计，快照变化也不能唯一恢复逐单撤补。
4. 需要订单存续、撤补或队列信息时，再验证 `SZ_Order` 的关联能力及重建成本，不将完整
   订单簿重建作为基础撤单特征的前置条件。

若启动比较，先固定模型、候选范围、选择数据、未消费的最终验证日期、判据和停止条件，
保持股票样本、观察窗口与信息可用时间一致。可先在深圳股票范围比较；上海尚未接入的
撤单信息不能填零来表示没有撤单。上述信息能补充观察维度，但尚无本研究的实验支持其
提高机会命中率、泛化或净收益。

实现核对基于 `0ab4b31d75741a91410e842cb7f7c89258ef24ca` 的
[归一化代码](../../src/data_system/normalize/level2.py)及
[现有测试](../../tests/data_system/normalize/test_level2.py)。本地运行
`test_normalize_baidu_delivery_preserves_milliseconds_and_source_multiplicity` 的沪深两例
均通过；深圳合成输入含正价格、正数量的 `ExecType=4`，输出仍只保留成交。
该证据仅覆盖现行过滤行为，不证明真实文件的撤单完整性、订单可关联性或预测价值。

### 数据版本边界

以下沿用 stock-1430 的条件性未来想法，不改变正式数据契约，也不构成实现承诺：

- Daily V2 可由 builder 唯一声明 `lookback_sessions=121`，读取 T 前 121 个正式

  仍失败，不缩小范围或替代输入。V2 独立存储，不覆盖/迁移/别名 V1；不预设同一
  set 的多版本配置、自动发现或批量构建。

- Minute、L2 Feature、Label、daily Feature、fusion 独立版本化；每个 fusion 版本明确绑定
  具体 daily/L2 set/version，producer、consumer、artifact/replay 使用精确 identity，
  不从存储推断上游或自动升级/降级，不做跨版本列 union/交集/重排/补 null 兼容。
