## Source identity

`source_name` 是本地 raw 分区身份；`raw_object` 是 broker 识别的源端对象；`outputs`
是该 raw source 直接产生的 processed dataset 名；`outputs=[]` 表示 raw-only。

Tushare 结构化 source 与 Level-2 文件 source 使用不同的选择权威：

- `TushareBroker._TUSHARE_SOURCES` 是 Standard 当前正式启用 source 的唯一 manifest。
  mapping key 同时固定为 `source_name`、`raw_object` 和单一同名 processed output，value
  是 Tushare API 名；存在于 mapping 表示启用，不存在表示当前 workflow 不执行。
- `data.sources` 只声明 Level-2 文件 source。每项必须显式提供 `enabled`、
  `broker=level2_ftp`、`group=offline_level2`、非空 `raw_object` 和完整 `outputs`；
  `enabled=false` 的文件 source 不参与执行。

配置不得声明 Tushare source，也不提供 `use_broker_sources`、group 总开关或其他隐式展开
机制。增加 Tushare capability 不得自动改变正式执行集合；改变 manifest 本身才改变 Standard
source 集。所有能够通过校验的 `data.sources` 都属于 Level-2，不存在被 workflow 静默忽略
的其他 group 或 broker 条目。

Feature 与 label 配置不使用 source group；其固定身份与字段语义由
[`docs/data/daily_feature_label_contract.md`](daily_feature_label_contract.md) 所有，执行编排
由 [`docs/offline_workflow_contract.md`](../offline_workflow_contract.md) 所有。

Broker implementation 的选择与绑定由
[`docs/offline_workflow_contract.md`](../offline_workflow_contract.md) 所有。Broker name
保留配置引用和 source identity 语义。运行时不得建立可变 register/freeze registry。
仅在需要来源 I/O 时构造 broker adapter，并在同一 workflow 内按 broker 复用。

Tushare 单日下载能力的调用形式为：

```python
payload_path: Path | None = broker.fetch(
    source_name=source_name,
    raw_object=raw_object,
    trade_date=trade_date,
    pm=path_manager,
)
```

`source_name`、`raw_object` 和交易日由调用方提供；broker identity 由具体 Broker 的
`name` 提供，source-native payload basename 由 Broker 确定。成功时直接返回已经写完的
正式 raw payload 路径；返回路径不表示 Meta 已提交，raw Meta 仍由 Step 提交。调用方不再
传递或接收 `DownloadPlan`，也不根据下载结果重新拼装 raw 路径。`None` 只表达本 owner
定义的源端无数据，不表达请求、文件写入或其他执行失败。

Broker 到 normalize callable 的关系固定为：

```text
tushare    -> normalize_tushare
level2_ftp -> normalize_level2
```

该关系不是 broker 配置中的 profile/version 选择器。所有 processed 输出固定写入 `v1`；
broker config 不声明 `normalize_profile`。

### 公告核验的证券状态

本节唯一拥有 `security_status/v1` 的数据语义；它补充历史名单、上市日期及停复牌来源
不能确定的证券状态，不覆盖或改写原始 `bak_basic`、`suspend_d`。上市状态与交易状态
独立：上市不等于当日可成交，停牌也不表示退市。回放消费及沿价估值由
[离线回放 owner](../offline_workflow_contract.md#真实行情到回放输入)定义。

状态核验必须指定证券、适用交易日、已确认的上市/交易状态、证据公开时间、原文 URL
和判断依据，并保留所补充的同日名单及停复牌来源位置。当前对象表达完整账户日状态，证据必须
在该日零时以前可见；盘中披露只能支持后续完整账户日，不能反向改写当天时段。
状态按证据能够证明的适用日期生成；
未来才披露的上市日、复牌日或更正不得提前影响历史成员及成交。只有日期的公告沿用
下一自然日零时才可见的保守约定；采集时间独立保存，不能充当历史公开时间。
确认待上市不要求知道未来上市日；发行阶段证据必须来自当时，空 list_date、缺行情或
后来上市本身都不能替代该证据。确认全天停牌需要对应 A 股证券的公告及期间覆盖，
不能将同一发行人的 H 股复牌套用到 A 股。证据不能消除冲突时继续保留未知。

原始核验输入 `SecurityStatusReviews` 固定包含 `version=v1`、`documents`、`reviews`。
其补充对象固定为同日 `stock_basic/v1`、`suspend_d/v1`，不另设内容指纹字段。
documents 保存公告身份、证券代码、标题、公开日期、URL 和采集时间。
每条 review 包含 `ts_code`、`trade_date`、可空的 `listing_status`
（pre_listing/listed/delisted）、`trading_status`（suspended/trading）、`available_ts_us`、
`evidence_refs` 和 `reason`。两种状态至少确认一种；交易状态必须同时确认 listed。
每个引用必须对应同一证券的原文 URL，原生公告身份与 URL 各自唯一，同一证券日唯一。

`ResolveSecurityStatusStep` 确认原文存在及原始输入 Meta 后发布三列 string：`symbol`、
`trade_date`、`resolution`；resolution 是上述 review 的 JSON。Parquet schema metadata
`security_status_inputs` 保存 stock_basic、suspend_d、reviews 三个对象相对于存储根的路径，
直接 upstream 指向核验输入的 Meta。生产者重新构造结果，表内容和来源路径相同时复用
payload，必要时更新直接 upstream 的 Meta 绑定；没有显式核验输入时不创建“已核实”对象。

核验结果由 data-system 发布为正式 V1 对象，Access 负责读取、schema、身份、来源路径
及所引用对象的 Meta 校验；回放仍只使用真实行情生成执行观察。同一明确引用按可信输入
使用，不将文件内容变化作为需要额外检测的失效模式。摘要不能证明证券身份、停复牌状态
或历史可见性；这些保证仍由原文关联、适用日期和公开时间规则建立。历史摘要与冻结材料
保留审计，新生产和消费不依赖摘要。原始来源冲突已经被充分权威证据解释时，仍保留冲突与处置依据，不把已确认
状态继续冒充未解决，也不删除来源行制造一致性。

除 `trade_calendar` 与 `dividend` 外，当前 Tushare source 按单日参数
`trade_date=YYYYMMDD` 查询。`trade_calendar` 固定查询 SSE，并以自然年作为唯一请求与对象
分区：

```text
trade_cal(exchange="SSE", start_date=YYYY0101, end_date=YYYY1231)
```

每个缺失自然年最多请求一次。全年 response 原样保存为该年的 raw Parquet；其他 source
response 仍按单日保存。Broker 不改变正式 processed 字段。

### 分红送转数据

`dividend` 按 `record_date=YYYYMMDD` 查询。raw/processed 路径仍使用统一的
`trade_date=YYYY-MM-DD` 分区，该日期在此数据集表示股权登记日，不是公告日、除权日或
支付日。按登记日查询能够确定账户权益的归属；按除权日只查询回测区间会遗漏先前登记、
本期到账的权利，这些跨区间权利由初始账户显式携带，不能从当前持仓反推。

Broker 显式请求来源默认字段及非默认的 base_date、base_share；raw 保存原始 response。
`processed/dividend/v1` 保留以下列。新增来源字段仍使用当前版本，
已入库分区从原始 response 同步重建，版本规则由[存储 owner](storage_layout.md#processedfeatures-与-labels)定义：

| 字段 | 正式含义 |
| --- | --- |
| ts_code、symbol | 保留含交易所的来源证券身份，并另存六位展示代码 |
| ann_date | 源端预案、决案公告日；不等于最终条款的历史可见时间 |
| end_date | 利润分配所属报告期结束日 |
| div_proc | 源端分配进度；预案、预披露与实施不能混为同一事件 |
| imp_ann_date、record_date、ex_date、pay_date、div_listdate | 实施公告日、登记日、除权除息日、派息日、红股上市日 |
| cash_div_tax | 每股税前现金红利，元/原股份；不是每十股金额 |
| stk_div | 每股送转合计比例；不再次叠加 stk_bo_rate 或 stk_co_rate |
| base_date | 来源基准日；不替代登记日或公开可见日期 |
| base_share | 来源基准股本从万股乘10000转换为股，nullable float64；保留发布精度，不擅自取整 |

日期转换为 `YYYY-MM-DD`，每股现金和送转比例转换为十进制文本，源端 null 保留；分配进度仅去除首尾空白。
base_date/base_share 未提供时为 null，不补0，不借用 total_share/float_share。基准股本只表示
分配方案的来源观察，不是账户登记持股，也不参与替代普通股东每股条款；DividendRecord 保留
这两个可选事实，既有候选身份、条款选择及账户权益公式不变。
现金保持元/原股份，送转保持新增股/原股份；不按每十股或百分数再次缩放。来源单位见
[Tushare 分红字段](https://tushare.pro/document/2?doc_id=103)。仅靠单位转换不能恢复来源
已舍入的股本精度，公开可见性仍由各条款的实施公告时间决定。
状态修正不会补出缺失的实施公告日，`实施 ` 且公告为空仍属于待核实事实。股票分配记录
可以没有现金侧，现金分红记录可以没有送转侧；两侧都未知不能当成确定的零分配。零行
response 必须生成上述列齐全的空对象，明确区别于尚未采集。单次 response 达到接口
2,000 行上限时无法证明完整，下载失败，不提交可能截断的对象。

#### 从来源记录到业务事件

本节唯一拥有 `corporate_actions/v1` 的数据语义。账户生命周期仍由
[公司行动与非交易账户事件](../offline_workflow_contract.md#公司行动与非交易账户事件)拥有。
`ResolveCorporateActionsStep` 在 dividend/v1 之后运行，按 `ts_code/end_date/record_date` 聚集
待解释记录。该键只是候选关联键，不是来源承诺的事件主键；不通过给公告行加序号或
ann_date 把重复记录变成多次到账，也不以数值一致证明分配对象相同。

普通分红送转以 `dividend/v1` 为主要来源；公告提供补充事实及已确认修正，逐笔公告核验
不是可执行事件的前置条件。
账户需要的是唯一的事件、普通股东的每股税前现金与送转比例、阶段日期及当时可见的条款；
这些事实可以由结构化来源提供。删除逐笔公告门槛后，这些必要事实和校验仍然存在，
因此该门槛不是记账的必要条件。反之，因 PDF 未采集或无法解析而拒绝一笔完整分红，会在
真实行情已经除息时漏记应收，不能把这类确定的缺项解释为更保守或更准确。

没有已确认修正时，同一候选先按实施公开时间选择适用方案，再归并等价观察；不要求恰好一行。
原始行与 dividend/v1 逐行保留。完整实施行按 imp_ann_date 选择较晚版本；较早实施方案以及
ann_date 明确早于该实施公告、但尚无实施公告日的旧观察，不继续否决后续实施方案。
例如新奥股份 2025-07-21 登记候选的旧观察为每股 0.81 元且没有实施公告日；
[2025-07-16 实施公告](https://static.cninfo.com.cn/finalpage/2025-07-16/1224176257.PDF)
及后续来源行明确每股 1.03 元，采用后者并从 07-17 才暴露条款。旧观察仍保留，不能把
1.03 元回填到旧预案的公告日。仅有更晚 ann_date 不证明实施方案已更正；无实施日期且
不能证明早于已知实施的观察仍为缺口。较晚缺项观察不能擦除较早明确事实，也不把不同
观察的互补缺项拼成合成行。单一来源方案必须在登记前已可见；需要登记后修订时，沿用
下述逐版本 review，不能把最终源行提前使用。

选择上述适用观察后，相同证券、报告期和登记日内，全部非空税前现金和送转比例
分别一致，除权、支付和上市日一致时，允许合并重复观察。预案／决案公告日 ann_date 的
差异不构成另一次实施。空金额表示该观察没有提供数值，不反驳另一行的明确金额。
优先采用现金和送转比例都明确的完整来源行，不将两条互补缺项拼成合成记录。没有完整行时，
若候选没有明确的非零现金，且存在一条正数送转、现金和派息日同时为空的原始观察，允许按
下述普通纯送转规则解释该观察；股份数量仍须由该行明确提供。例如 002226 的两条观察只有预案／决案
日期不同，实施日、每股 0.065 元和结算日期一致；持有 1,000 股应形成一次 65 元权益，
重复观察不应使权益变成未知或 130 元。同一实施公开时间的不同非空金额和不同阶段日分别保留
different_distribution_terms 与 different_phase_dates，不按条目顺序选择。

普通分红送转的来源实施公告日和除权日均须提供；优先在金额明确的完整行中选择，没有完整行才在可解释为
纯送转的原始行中选择。各组内按实施公告日取较晚者，相同实施公告日时按
ann_date 取较晚者（缺失排在已提供日期之前），只为稳定选择原始观察，不生成合成行。
ann_date 排序只用于等价观察，不能消除同一实施版本的真实冲突。条款从所选完整行的
imp_ann_date 结束后下一自然日 00:00 可见，避免采用较早的争议日期；缺值观察不把另一行
的明确金额提前到自己的公开日。所选实施公告日必须先于登记日，登记日先于除权日；
非零权益有对应支付或上市日，日期不早于除权日，零权益没有对应结算日。

普通送转范围仍限报告期为 03-31、06-30、09-30 或 12-31 的候选；明确正现金、零送转的
纯现金分红不受这一报告期限制。季度末不是现金分红可执行的必要事实，例如贵州茅台
2023 年特别分红的来源报告期为 11-21，每股现金 19.106 元，12-19 登记、12-20 除息及
支付，不能仅因报告期格式拒绝；金额、日期及股东范围见
[当时实施公告](https://www.sse.com.cn/disclosure/listedinfo/announcement/c/new/2023-12-14/600519_20231214_WR1C.pdf)。
非季度末的送转记录仍需明确分配性质与受益对象，不能
将重整总转增比例当作普通股东权益。

普通送转不要求来源显式填写现金零值：在上述普通范围内，正数送转及阶段日期有效，现金
和派息日同时为空，且没有明确非零现金、已确认现金权益或冲突时，将账户现金解释为零。
`dividend/v1` 与 `source_record.cash_div_tax` 保留原始 null，转换为可执行条款时才令
`cash_per_share = 0`，pay_date 仍为空；不增加来源标记、平行数据集或额外状态。null 保存
“供应商未填写数值”，0 表示“本次普通账户无现金权益”，不能混淆两个层次，也不将此规则
表述成供应商对所有空值的承诺。存在派息日、股份也为空、明确现金权益或冲突时不能按零
执行；零送转与空现金也不能据此认定 not_entitled。已确认修正仍优先，版本可见时间不变。

例如八一钢铁 600581 的 2018-04-19 登记来源为每股转增 1 股，现金与派息日为空，04-20
除权、04-23 上市。[当时实施公告](https://static.cninfo.com.cn/finalpage/2018-04-16/1204628906.PDF)
完整说明资本公积转增、全体股东及阶段日期，没有单独写“现金为零”。要求这句固定措辞
会把完整纯送转误作权益缺失。该例解释为零现金、每股新增 1 股，同时完整保留源行空值；
持有 100 股增加 100 股，不形成现金应收或支付。公告自动提取同样允许完整普通纯送转方案
不写零现金句子，但提到现金分配而金额无法确定，或存在尚未解释的现金支付安排时仍保留
缺口，不能把文字提取遗漏当成纯送转。

同一证券、登记日的其他候选（包括独立公告）尚未明确关联时，不自动选择一个或相加。
满足条件的结果保存所选的原始 `source_record`（包括上述可解释的现金 null），
action_id 为 `dividend:<candidate_id>:ordinary_shareholder`，reason 为 `ordinary_dividend_source`；
它表示采用来源事实，不表示已独立证明受益对象或核验公告。标准报告期只是限定本次普通
送转处理范围，不能证明不存在重整或差异化分配。已知特殊事件及冲突继续进入异常处理。

来源可见性不使用预案 ann_date 或本次采集时间提前暴露实施条款。公司行动链路信任
已接收的来源事实和已确认修正，不将文件被
替换、原始数据被事后改写作为运行时需要检测的失效模式；不为这些假设增加内容摘要、
快照绑定或重新核验门槛。已知更正仍按公开时间保存原版和修订版，不能将最终条款回填到
原公告日。登记前已公开分配安排、登记后才确定净分配比例的事件，按下述待定条款处理；
只有事后最终值、没有当时可见登记安排时仍保留未解决。这里的时间约束决定条款何时
可用于账户，不要求另建供应商历史版本或文件完整性证明。

公告承担已确认修正、异常消歧、受益对象核实和来源遗漏补充。选择来源以阶段所缺的业务
事实为依据，不以 PDF 数量或逐篇完整提取为验收条件。普通来源已满足的事实不要求重复
公告证明；特殊事件须补齐适用于合资格普通持仓的净权益，不能用公司整体转增比例代替。
直接公布的净比例已足以计算时，不再强制要求公告同时给出分子、分母。不同公告可以提供
同一事件的不同阶段事实；已确认重复且不改变条款、身份、阶段或可见时间的材料不增加
入账门槛。首份公告缺少可独立执行的事实，后续完整实施公告在登记前已公开时，可以从后者
开始形成计划，不要求首份先通过提取。后续文件只公布除权参考价时，只更新参考事实，沿用
已经确认的普通股东权益和阶段日期；它不必重述现金、净获配比例和全部日期。任何时点只
使用已经公开的版本，不能将结果日期倒写到首次方案。尚未判明的相关更正与真实冲突不能
当作重复材料跳过；同日无法排序的不同值、阶段日冲突、晚到修订仍按下述限制处理。核验输入是
`raw/announcements/corporate_action_reviews/trade_date=<登记日>/reviews.json` 及其 Meta；
JSON 为 `CorporateActionReview` 数组。每项包含 candidate_id、related_sources、独立 action_id、
shareholder_scope、record_date、ex_date、pay_date、div_listdate、terms、evidence_refs、reason。
related_sources 是其他候选关联键的唯一列表；空列表表示该事件只关联主候选。
主候选不得再次出现在列表中，同一候选不能绑定到两个核验事件；关联候选必须属于同一证券和登记日。
跨候选关联必须由公告证明它们属于同一计划，不能仅凭相同证券、登记日、金额或不同报告期自动归并。
自动提取用证券身份、来源实施公告日和原文登记日关联事件，不要求来源报告期标签与
公告标题逐字一致；缺少实施公告日关联时，仍需正文或标题的期间与登记日共同确认。
标题只用于发现候选，不以“实施公告”“实施的公告”等固定结尾作为事实成立条件；
“事项实施的提示性公告”“实施暨风险提示的公告”和正文完整的进展公告均可提供实施事实。
正文仍须明确当前普通股东权益及必要阶段日；预案、尚需审批和已经取消的方案不能仅凭
出现登记日就当成已实施。后续参考结果或修订可以通过原文登记日，或明确引用的前公告
名称及公开日关联事件，不必重述全部条款。仅修改公司汇总数、且明确其余内容不变的材料，
在变更字段不涉及每股权益、适用范围、阶段日或参考价时跳过；例如海泰新光
[2023-06-09 更正](https://static.cninfo.com.cn/finalpage/2023-06-09/1217021915.PDF)
仅更正新增无限售流通股总数，不能因此拒绝原文明确的每股现金 0.80 元、转增 0.4 股。
无法确定修订影响范围时仍须处理，不能把所有带“其他内容不变”的文件都忽略。
多个候选提取到同一个原生公告事件，且阶段日期、普通股东条款及公开版本完全一致时，
自动归入该事件的 related_sources；事实不同则保留关联冲突，不任取一个或重复记账。
例如新华制药 2018-01-25 登记来源的两个报告期标记，关联同一份 01-20 特别派息实施公告；
每股 0.03 元只形成一次权益，报告期较晚不能被解释为又派发一次。
每个候选仍发布自己的 resolution，保存同一份完整 review；账户按 action_id 只登记、派发一次。
修正以候选身份关联来源，不绑定源行内容指纹；核验身份重复、没有有效来源的核验或非法
条款直接失败。同一候选内等价观察按上述来源规则归并；原始行继续保留，跨候选事件关联
和真实条款冲突不能通过删行消除。
公告链接及解释属于输入事实，不允许在回测代码里写股票代码特例。
`CollectAnnouncementsStep → ExtractDistributionTermsStep → ResolveCorporateActionsStep` 生产这些核验与解析事实；
采集边界、原文证据、人工复核输入及未覆盖能力见[公告流程](#announcement-verification-todo)。

经完整原文核验的实施公告也可独立产生 V1 事件，不要求 Tushare 已返回对应候选。
复核输入的 announcement_source 保存原生渠道、公告 ID、原证券代码、标题、公开日期、
已核实的精确公开时刻及原文 URL；candidate_id 为 `<渠道>:<公告ID>`，
action_id 为 `<渠道>:<公告ID>:ordinary_shareholder`。独立来源不能伪造 Tushare 行或报告期；
仍须完整采集该证券的声明公告窗口、核对公告身份和索引、显式提供各阶段已知的条款及待定项。
已确认修正不因无关公告加入集合或文件编码变化而要求重新核验。
登记日 corporate_actions 投影要求同日 dividend/v1 覆盖对象已准备，真实空集合可以满足这一前提，它不成为
这次公告事件的分红证据。来源引用同时保存覆盖对象、公告集合、原文与复核输入的位置。
以后 dividend 补到同一事件时，显式将其候选加入同一 review 的 related_sources；
保留公告主身份和原 action_id，每个来源各有处置、账户只执行一次。未完成关联时不能
同时批准两次分配，也不能仅按同日同证券自动合并。首次实现以原代码直接对应的公告为
边界；公告代码与账户证券不一致时须先补齐明确身份关联，不能推断代码相同或股份连续。

当前账户口径 `ordinary_shareholder` 只模拟符合该次分配资格的二级市场普通流通股持仓。
公告单列的大股东、回购专户、管理人、重整投资人、债权人，以及受特殊股份来源排除条款
影响的持仓，均不在模拟范围内。因此不建立股东名单或股份来源追踪状态，也不因公告存在
这些排除条款而否定已明确的合资格普通持仓权益。这是账户的建模前提，不是“所有个人
账户实际都合资格”的事实判断；税前记账也不能改变真实持仓资格。
在此范围内，以登记日收盘持仓数量乘以该事件适用于普通股东的实际净分配比例，不能仅凭
曾经买入判断权益，也不能套用公司整体转增比例或另一事件的中小股东比例。登记前卖出的
部分没有权益，登记后卖出不撤销已登记权益；普通股东实际净分配可以为零。
例如供销大集 2021-12-30 登记事件，公司每股总转增 2.2035714 股，合资格普通持仓每股
净获配 2.1898786 股，统一参考价为 1.80 元。被排除股东在指定期间转出的股份不获配这一
限制仍是真实公告事实，但该类持仓不由本模型表达。只看公司总比例会多记股份，只看价格
变化则会漏记普通股东实际获配，两者都不能替代具体事件的净权益。

terms 逐版本保存 published_date、可选 published_ts_us、cash_per_share、shares_per_share、
reference_cash_per_share、reference_shares_per_share 和可选 reference_price，已知金额与比例为 Decimal。
在显式确认的分配安排中，cash_per_share 或 shares_per_share 为 null 表示该项存在但数值待定，
支付、上市日期也可以分批披露；零表示明确无该项权益，不能把待定项填零。该解释用于
公告事实与账户阶段，不改变普通 dividend 缺项的准入规则。resolved 表示事件身份、登记安排
及条款含义已明确、可以驱动账户阶段，不保证每个阶段的数值已经可见；未到计算时点的
待定版本不否定该事件，计算时点仍无数值时由账户报告 pending_distribution_terms。
参考值有两种互斥表达：完整的一对参考现金和股份参数，或公告直接确定的正值 reference_price。
直接参考价不拆成虚构现金或股份；普通股东零权益也可以同时发生参考价调整。
两项公式参数必须同时为数值或同时为 null；三项参考值全为 null 只表示该早期权益版本
尚无可用参考值，不能据此推断价格不变。参考版本缺失不构成整笔事件拒绝；登记与确认权益不要求先知道市场参考价，
估值是否可用由工作流按行情和明确假设判断。已确认各版本普通股东现金
及新增股份均为零的事件，不以参考值完整为来源处置门槛；它不产生账户分配权益，估值缺口
由工作流按实际暴露和当时可见价格单独报告。供销大集 12 月 27 日实施公告提供权益和日期，
12 月 30 日提示公告才确定 1.80 元，不能把最终价格回填到首版。
已确认参考参数不能默认复制账户分配金额；source_record 本身不提供交易所参考事实。
只模拟普通股东不意味着将市场参考扣减当成普通股东现金。例如舒华体育 2024-05-08
登记事件，普通股东每股税前现金为 0.30 元，差异化除息参考扣减为 0.2974 元。

0.25 元表述，因此该案例曾被撤销自动批准；这是真实文字冲突，不是 0.30 与 0.2974
分别承担不同用途造成的歧义。同日公开的
[法律意见书第 3–4 页](https://static.cninfo.com.cn/finalpage/2024-04-26/1219837425.PDF)
明确普通股东每股 0.30 元，408,169,000 股对应现金总额 122,450,700 元，并另列参考扣减
0.2974 元，支持显式消歧。复核同时保留两份原件与说明，从 04-27 才暴露该版条款；
不能据此自动忽略其他公告中的金额冲突，也不必模拟回购专户的现金权益。

事实版本按证据支持的可见时刻递增：只有日期时使用下一自然日 00:00；有原始索引
支持的精确时刻时保存 UTC 微秒 published_ts_us，并核对上海本地日期等于 published_date。
午夜占位不声明精确时间。后续公开的比例、日期、参考价只从该版可见时刻起使用，不能回填
首份公告。记录登记日实际持仓不依赖未来是否出现公告；后来才明确历史资格日时，只能读取

公告日期较新就消除；明确更正可更新尚未执行阶段，已确认或已结算权益不能静默改写。

例如 `002986`、`002727` 原公告的支付日早于除权日，原件及冲突均保留；更正公开后才形成
合法日程，不伪造更正前的可执行版本。雅博等事件的原文只有分配总数而没有分母，则是正常的
事实等待，不是日期矛盾或解析失败。已知数值不因后续公告省略而退回 null。参考价更新只作用
于还未被真实行情替代的临时估值；后补事实不使早期带缺口的净值变成完整收益。

### 事件进入、事实补齐与账户投影

`announcement_facts/v1` 是披露日事实表，不是全量核验通过表。每条记录保留原生公告身份、
稳定 event_id、证券、来源、公开时间、系统观察时间、事件种类、分配状态，以及已披露的
登记/除权/支付/到账/上市日期、普通股东税前现金及净股份比例、分配总数、受益持股分母和
市场参考参数。未披露字段为 null；已确认零、附条件安排、取消及冲突各有独立表达。
分子先到、分母后到可分别保存；只有实际数量计算才要求完整分母或正式净比例。公司整体
扩股比例不填入普通股东净比例，除权参考价也不替代个人应得金额。

事件初始身份采用首次关联公告的 `source:announcement_id`，不含未来才明确的登记日。
自动跨文档关联需要同证券、明确引用原公告标题和日期；只有同公司、同日期、最新文件或
相似比例不足以归并。不能证明关联的材料独立保留；多个引用指向不同事件时标记
`event_link` 冲突，不猜测唯一事件。已确认 review 及其 related_sources 继续优先；与既有
登记处置重叠的公告不另发一笔权益，特殊事件缺关联时保留账户关联待处理诊断。

同一事件按公开时间累计事实。后文省略某项不删除已知值；相同原生公告或相同事实不重复
登记。不同值默认是冲突，明确更正且有严格较晚的可见时间才能替换该字段；同日只有日期的
互相矛盾文本没有可靠先后，不按公告 ID 排序决定真值。取消是后续事实，不删除事件历史。
真实更正若影响已确认/结算账户阶段，须独立账户调整，不能重写历史流水。

时间分为业务阶段时间、公开可见时间、系统实际观察时间。历史公共信息回放按公开时间
过滤；复现实盘信息延迟时再要求 observed_at 不晚于当时系统时刻。今天下载的历史文件不
证明系统过去已经采集，也不证明源端历史数据库版本；这里不添加摘要或原文件变化检测。
`Access.announcement_history/announcement_events` 必须先过滤再累计。筛选、特征和账户
共享该视图，不能拿最终修正版构造早期特征，也不能只保留最后成功实施的事件作为训练样本。
当前不擅自增加模型特征列；具体特征、标签成熟日仍由对应 owner 定义。

公告 facts 保存成功、事件足够关联、权益足够计算、可用现金/股份完成入账是不同结果。
正常等待补充、解析问题、事实冲突和账户因缺事实不能推进分别保留，不能把前两者都叫
“公告核验不通过”，也不以未解决数量归零代替数据质量验收。后续公告可能没有新增必要

## 正式交易日历

`processed/trade_calendar/v1` 是唯一正式交易日历，以 `year=YYYY` 保存每个自然年的一个
正式对象。payload 包含该年 Tushare response 转换后的全部行，schema 精确为：

```text
trade_date: string  # Tushare cal_date 归一化为 YYYY-MM-DD
is_open: bool
```

Tushare `trade_cal` 是日历日期完整性、唯一性、请求范围、交易所和 `is_open` 取值的正式
数据源权威。本系统不重复检查这些 source 业务不变量；normalize 只执行字段选择、日期格式
转换和 `0`/`1` 到 boolean 的类型映射。外部请求失败、空 response、缺少转换所需字段或
`cal_date` 无法完成日期格式转换仍必须失败。

有效 Meta 证明该自然年对象已经正式提交，不表示其中每一行都开市。正式交易日定义为：

```text
row in valid yearly trade_calendar object AND is_open == true
```

开市日和休市日都保存在同一个年度 payload 中。查询范围涉及的任一年度对象缺失时，整个
范围不可用。Producer 发现有效年度 Processed Meta 时直接复用，不隐式刷新或覆盖；日历
刷新不是当前 offline data workflow 的行为。旧 `trade_date=YYYY-MM-DD` 日历对象不构成
年度正式对象，Access 不读取该旧布局。

## Tushare processed 单位

Raw 保存来源 response 的字段、数值和单位。Normalize 是来源单位进入系统的唯一换算边界；
Access、Feature、Label 与回放消费 processed 单位，不再解释手、千元、万元或百分数。
本节拥有下表的来源映射；分红字段由[分红 owner](#dividend)拥有，
Level-2 的证券类型、价格编码与股票股数由[Level-2 owner](level2_normalization.md#raw-到-processed-字段关系)拥有。

当前股票事实采用股、人民币元、元/股和小数比例（1 表示 100%）。单位按具体 API 与字段绑定，
不按列名后缀或数值大小推断。字段名保留，例如 pct_chg 的 processed 数值仍按小数比例解释。

| 本地数据集（源 API） | 字段 | 来源单位 → processed 单位 | 转换及类型 |
| --- | --- | --- | --- |
| daily_bar（daily） | vol、ah_vol | 手 → 股 | ×100，nullable int64 |
| daily_bar（daily） | amount、ah_amount | 千元 → 元 | ×1000，float64 |
| daily_bar（daily） | pct_chg | 百分数 → 小数收益率 | ×0.01，float64 |
| daily_basic | total_share、float_share、free_share | 万股 → 股 | ×10000，float64 |
| daily_basic | total_mv、circ_mv | 万元 → 元 | ×10000，float64 |
| daily_basic | turnover_rate、turnover_rate_f、dv_ratio、dv_ttm | 百分数 → 小数比例 | ×0.01，float64 |
| stock_basic（bak_basic） | total_share、float_share | 亿股 → 股 | ×100000000，float64 |
| stock_basic（bak_basic） | rev_yoy、profit_yoy、gpr、npr | 百分数 → 小数比例 | ×0.01，float64 |
| moneyflow | buy/sell 的 sm、md、lg、elg 档 vol 及 net_mf_vol | 手 → 股 | ×100，nullable int64；净量允许负数 |
| moneyflow | 上述各档 amount 及 net_mf_amount | 万元 → 元 | ×10000，float64；净额允许负数 |

来源依据：[daily](https://tushare.pro/document/2?doc_id=27)、
[daily_basic](https://tushare.pro/document/2?doc_id=32)、
[bak_basic](https://tushare.pro/document/2?doc_id=262)、
[moneyflow](https://tushare.pro/document/2?doc_id=170)。同名 total_share 在 daily_basic 与
bak_basic 的源尺度相差一万倍，因此不能共享仅按字段名选择的转换规则。

采用股使价格乘数量直接得到元，避免成交、持仓和股本计算重复乘100；采用元使成交额、
市值和资金流金额能按同一尺度计算。例：13.01 手转换为1301股，不先取整手数，也不要求
成交股数为100的整数倍。手数使用精确十进制转换，非空值必须能无损落入 int64 股数；
不足一股的尾数、非有限值或溢出必须失败，daily_bar 的量还必须非负。来源 null 保留，
不能作为零成交或补齐盘后覆盖的依据。其他参与换算的非空数值必须有限，转换失败或溢出
失败整个对象；不截断、不补零。换算只处理已提供的通用源字段，不凭缺列合成事实。

股本是供应商发布的观察值，采用 float64 保留来源所提供的精度，不因以股表示而宣称精确到
一股，也不擅自取整。行情价格、金额与比例沿用 float64，不提前舍入到两位或三位小数；
金额单位为元不限制小数位。账户精确金额及公司行动条款继续沿用各自 Decimal 契约。
百分比转比例不要求数值在0到1内；收益和增长可为负，换手率可超过1。

以下字段数值不缩放：股票价格和绝对涨跌额；daily_basic 的 volume_ratio、pe、pe_ttm、pb、
ps、ps_ttm 等倍数；adj_factor；已以元提供的 margin/margin_detail 金额。cyq_perf 的
cost_5pct 等列表示成本价格，字段名中的分位不触发百分比换算。

尚不能确定映射的字段继续保留 source-native 语义，不宣称已统一：top_list 的金额与比例、
cyq_perf.winner_rate、bak_basic 的资产金额及 reserved/undp 等财务字段。前两者的官方字段
表缺少明确单位，后者仍需明确币种及未注明字段的尺度。margin 汇总的 rqyl/rqmcl 混合
股、份、手，无法用一个系数转换成股；margin_detail 的数量及非股票 Level-2 数量继续按
证券类型和原 owner 解释。源币种不同不能仅改单位名称转换成人民币。

单位一致只保证量纲可运算，不证明统计范围一致。单笔、累计快照、盘口存量、不同股本分母、
复权基准、主动买卖及 tick-rule 方向必须分别保留。日线与 Level-2 对账前须先确认证券、日期、
事件、时段和来源精度；日线成交额不要求等于收盘价乘成交量。

## Daily bar

`processed/daily_bar/v1` 是行情事实，不是交易日历。它只能证明某个正式交易日的日线行情
已经落地；其存在或缺失不得改变 `trade_calendar` 给出的交易日序列。

Workflow 不为 `is_open=false` 的日期请求 `daily_bar`。`is_open=true` 时缺少
`daily_bar` 是数据缺失并必须失败；feature、label、training 或 backtest 不得跳过该日并
把后续日期当作替代交易日。

该对象保留 [Tushare A 股日线](https://tushare.pro/document/2?doc_id=27) 的未复权价格，
OHLC、pre_close、change 为元/股，vol/ah_vol 为股，amount/ah_amount 为元，pct_chg 为
小数收益率；转换由上节唯一规定。pre_close 保留来源除权参考价含义，不能等同于上一日
原始收盘价。回放价格/时间映射由
[offline 工作流契约](../offline_workflow_contract.md#真实行情到回放输入)拥有。
Broker 显式请求 ts_code、trade_date、open、high、low、close、pre_close、change、pct_chg、
vol、amount、ah_vol、ah_amount。Processed 按该顺序保存，最后追加 symbol。
ah_vol/ah_amount 是可空的盘后独立观察，来源未提供字段或值时保留 null，不补0；
历史 raw 缺少这两个可选字段时仍只表达未知。该规则不证明日线主量额与盘后量额的包含关系，
也不允许相加生成总量；当前 Level-2 不声明盘后固定价格渠道覆盖。
Tushare 停牌期间不提供该证券日线，但不能反向推断每次日线缺失都属于停牌；缺行原因
仍需核实。缺行不表示零成交的完整日线，也不得使用后续日线补齐。
源端日线在盘后入库，其日标签不是精确的历史发布时刻证明。

单位调整继续使用 v1。已经提交的旧单位 processed 必须从明确 raw 重建，不能在读取时自动
猜测或兼容，也不能将旧 processed 再作为 Normalize 输入。有效 Meta 的命中不表示历史
对象已经完成单位调整。正式切换须同时处理受影响的 Feature、模型输入和回放消费，并验证
上下游尺度一致；单次普通 workflow 不隐式重写历史对象。缺少可选源字段的历史事实只有
重新取得来源观察才能补齐，不能通过单位转换生成。

## Source no-data 边界

单日 Tushare source 成功返回 `DataFrame` 即表示已取得 payload；零行 `DataFrame` 是有效
空记录集合，Broker 必须照常写入 raw payload 并返回该文件的 `Path`，不得把它转换为下载
失败。只有源端返回 `None` 时，单日 Tushare Broker 才返回 `None`。

`stock_st` 的 `2019-04-01` 是该边界的正式案例：源端成功响应且记录集合为零行，返回的
DataFrame 不携带列。Normalize 必须构造空 `symbol` 列，Producer 必须提交
`raw/tushare/stock_st/trade_date=2019-04-01/data.parquet` 及同目录 `meta.json`；该对象表示
Tushare 对当日查询返回的 ST 记录集合为空。本系统以该 source response 的记录集合为权威，
不在运行时使用外部来源复核其事实完整性；因此该对象不表示下载失败或数据缺失，也不得使用
`2019-03-29`、`2019-04-02` 或其他日期的记录填充。

`suspend_d` 的零行 response 使用相同的空 `symbol` 列构造规则。该规则只使空集合能够由
Access 直接消费，不增加事件记录。

Transport、认证、response 类型、非空 response 的必要字段缺失或没有上述可空映射的字段
转换失败必须传播为错误。`trade_calendar` 必须包含记录；对请求自然年返回 `None` 或零行
response 都必须使日历 producer 失败。其他 source 的 range 聚合和缺失失败语义由 workflow
owner 定义。
